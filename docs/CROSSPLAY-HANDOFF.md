# AltarSMP crossplay handoff — the series, the package, the one command

This document ships as the last commit of the six-commit Bedrock/Geyser
crossplay series. It is written so the whole series can be re-applied to the
base commit with one command, the package can be regenerated byte-for-byte
from the committed inputs, and every guarantee the package makes can be
re-verified mechanically.

## What the package is

`AltarSMP-Custom-Content/` is the Bedrock/Geyser crossplay package for the
AltarSMP Fabric port (2.0.5):

- `geyser/altarsmp-custom-items.json` — Geyser custom-item mappings
  (`format_version` 2, `legacy` definitions keyed on `custom_model_data`,
  one entry per Java `(item, model data)` pair — 46 pairs over 24 base
  items). Copy into Geyser's `custom_mappings/` folder.
- `packs/pack.zip` — the Bedrock resource pack: `manifest.json`
  (format_version 2, uuid5 identity, version 2.0.5,
  `min_engine_version` 1.21.0), 46 Bedrock item definitions
  (`items/*.json`), `textures/item_texture.json`, 46 rendered 128x128 icons
  (`textures/items/`), 34 attachables + geometries + packed atlases for the
  3D weapon/ability models, and the 96 ability tooltip artwork pngs restored
  from the Java pack. Copy into Geyser's `resource_packs/` folder.
- `inventory.json` — all sixty Java catalogue entries cross-referenced to
  their Bedrock item (50 model-mapped, 10 deliberate vanilla-look) with the
  alias grouping where two Java entries share one visual.

Everything in the package is generated by `tools/crossplay/` (pure python3
stdlib — `zlib`/`struct` PNG codec, no PIL, no numpy, no network) from
committed inputs only: `AltarSMP-ResourcePack.zip` (authoritative assets,
per `docs/asset-audit.md`), `fabric-mod/src/main/resources/altarsmp/content/*.json`
(the 60 mapped entries) and the mod icon.

## The one command that applies the whole series

From a checkout of the base commit `fac814a4e80ef9d3043753e6b5128bab99558e9b`
("Add files via upload") with this document's `patches/` directory beside it:

```sh
git am patches/0001-*.patch patches/0002-*.patch patches/0003-*.patch \
        patches/0004-*.patch patches/0005-*.patch patches/0006-*.patch
```

(`git am patches/0*.patch` is the same thing.) Applying the series on top of
`fac814a` reproduces the tip tree exactly — verified in a throwaway clone:
`git am` of patches `0001`–`0005` yields the commit-5 tree
`f33e1b6666e18070dd4d1c136ece04d3a4964556`, and the regenerated sixth patch
adds `patches/0001`–`0005` plus this document on top of it, yielding this
commit's tree — the series' tip tree. Check it after applying:

```sh
git rev-parse HEAD^{tree}    # recorded in commit 6's message
```

The tip-tree value lives in commit 6's message (and nowhere in the trees)
on purpose: a tree cannot contain its own hash, so the message — bytes no
tree carries — is the honest place for the record. Patch 6 is this commit
itself, so a freshly generated `patches/0006` (see below) is an untracked
extra the trees do not carry.

## How to regenerate the package

```sh
python3 tools/crossplay/generate_custom_content.py
```

rewrites `AltarSMP-Custom-Content/` in place (mapping, pack, inventory,
README). It is deterministic: sorted zip entries, fixed 1980-02-01
timestamps, fixed compression level, stable JSON key order, uuid5 manifest
identity, no absolute paths, no timestamps or hostnames in generated files.
Two clean runs produce identical bytes — verify:

```sh
sha256sum AltarSMP-Custom-Content/packs/pack.zip
python3 tools/crossplay/generate_custom_content.py
sha256sum AltarSMP-Custom-Content/packs/pack.zip   # unchanged
```

```sh
git log --oneline fac814a..HEAD                       # the six subjects
git rev-parse HEAD^{tree}                             # f33e1b6... (tip tree)
```

## The 29 validator checks

1. Authoritative inputs are present: `AltarSMP-ResourcePack.zip`, the content
   directory and the mod icon the generator reads.
2. `fabric-mod/gradle.properties` declares `mod_version=2.0.5`.
3. Catalogue counts: `armor.json` 8, `items.json` 22, `weapons_s1.json` 24,
   `weapons_s2.json` 6 entries carrying `custom_model_data` (60 mapped).
4. Every `custom_model_data` is a non-negative integer.
5. No two Java entries collide on `(base material, custom_model_data)` in the
   Geyser mapping — two Bedrock items can never claim one Java look.
6. Entries recorded as vanilla-looking really sit on dispatcher thresholds
   the pack does not declare (the reserved discriminators).
7. All mapped `custom_model_data` values fall inside the dispatcher's
   declared thresholds for their base material (exact-threshold dispatch;
   sibling-borrowed entries ride their sibling's slot).
8. `inventory.json` covers all 60 entries: 50 model-mapped, 10 deliberate
   vanilla-look, 46 distinct Bedrock items.
9. The Geyser mapping declares `format_version` 2.
10. Every mapping key is a namespaced Java item id (`minecraft:...`).
11. Every definition is a `legacy` one with an integer `custom_model_data`.
12. Bedrock identifiers are unique across the whole mapping.
13. Identifiers are `altarsmp:`-namespaced lowercase snake_case.
14. Every Geyser `bedrock_identifier` resolves to a Bedrock item definition
    shipped in the pack.
15. Every `(java id, cmd)` pair in the mapping traces to the content
    catalogue — the mapping invents nothing.
16. `manifest.json`: format_version 2 and valid, distinct v4-format
    header/module UUIDs.
17. `manifest.json`: version `[2, 0, 5]` and integer `min_engine_version`.
18. Pack zip entries are safe — no `..`, no absolute paths, no backslashes,
    no drive letters (zips cleanly, no path traversal).
19. Pack zip entry names are unique and sorted; every timestamp is the fixed
    1980-02-01 determinism stamp.
20. Every item definition: format_version `1.21.0`, identifier matches the
    file name, `menu_category` present.
21. The pack ships exactly one definition per distinct Bedrock item (46).
22. Every definition's `minecraft:icon` resolves to a packed texture that
    exists in `textures/items/`, and every icon file is the expected square
    power-of-two size (128x128).
23. `item_texture.json` entries and `textures/items/*.png` match exactly in
    both directions — all texture references resolve.
24. Auto-fit / no clipping: every rendered 3D-model icon's opaque pixels stay
    inside the canvas with a one-pixel border (flat full-bleed sprites are
    exempt by their inventory `model_kind`).
25. Every attachable's identifier, geometry and texture references resolve
    inside the pack (34 attachables).
26. Every geometry face UV rect fits inside its atlas (uv and uv+uv_size
    within `texture_width`/`texture_height`, which match the packed png).
27. Face UV rects are sampled against each model's honoured Blockbench
    `texture_size` basis: exports laid out on the declared texture-size grid
    use it, vanilla-grid exports use the vanilla 16 scheme (where
    `texture_size` is Blockbench-only metadata). Recomputing every rect as
    min(raw)/basis x sub-texture size + the atlas offset reproduces the
    shipped geometry exactly, with image-space v.
28. Ability artwork: every `tooltip_style` in the catalogue resolves to a
    background+frame pair in the pack, and all 96 artwork pngs are shipped.
29. `pack.zip` is byte-for-byte reproducible: regenerating the package in the
    validator's own process reproduces the shipped archive's sha256.

## Rendering conventions (what the icons are)

The icons are one orthographic "gui" view of each custom item's Java model:
per-element boxes, element rotations and `display.gui` applied (rotation in
Z, Y, X vector order — the order vanilla's ItemTransform ends up with through
JOML's rotationXYZ), backface-culled, painter-sorted per element centroid,
barycentric face fill with alpha, per-face UV sampling under the model's
honoured basis (see check 27). The projection is computed in canvas-relative
units with uniform scale-to-fit, so oversized models shrink to fit and never
clip or stretch. Approximations, on purpose and documented: no perspective,
no lighting, painter's algorithm instead of a z-buffer, geometry face rects
normalise mirrored (reversed) source UVs. The Bedrock attachables carry the
same geometry with x mirrored / z recentred into Bedrock's coordinate space
and single-axis rotations preserved as cube rotation/pivot.
